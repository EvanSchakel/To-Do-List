## 2024-05-07 - Avoid SELECT before DELETE in Spring Data JPA
**Learning:** By default, Spring Data JPA's `deleteById` and manual "check existence then delete" workflows cause an unnecessary SELECT query before the actual DELETE query. In a high-throughput system, this N+1 like behavior is a performance bottleneck.
**Action:** Use a custom `@Modifying` JPQL `@Query("DELETE FROM Entity e WHERE e.id = :id")` that returns the number of affected rows to achieve a deletion in a single database roundtrip, as long as JPA lifecycle callbacks (`@PreRemove`) or entity-level cascades are not required.
## 2024-05-15 - Optimize Spring Data JPA query performance via @Transactional boundaries
**Learning:** In Spring Data JPA, read-only transactions can benefit from `@Transactional(readOnly = true)` to disable Hibernate's dirty checking, reducing memory overhead and improving read speed. Further, for fetch-modify-save operations (like an `updateTask`), missing a `@Transactional` boundary causes the fetched entity to be detached immediately after the initial fetch query completes. As a result, calling `save()` triggers a redundant SELECT query before the final UPDATE.
**Action:** Always add `@Transactional(readOnly = true)` on the class level for services performing database operations and override it with `@Transactional` on write methods to prevent entities from becoming detached during multi-step operations.
