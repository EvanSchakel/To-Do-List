## 2024-05-08 - Fixed Overly Permissive CORS Configuration
**Vulnerability:** The application was configured with `allowedOrigins("*")` in `WebConfig.java`, which allows any website to make requests to the API.
**Learning:** This architectural gap means the API could be vulnerable to cross-origin attacks because the browser would allow any origin to access the resources. We need to define exactly which origins should have access.
**Prevention:** Avoid hardcoding `*` for CORS origins. Instead, inject the allowed origins using application properties (e.g., `@Value("${cors.allowed-origins}")`), and configure a safe default restrict value (like `http://localhost:3000` for local dev) in `application.properties`. For production environments, override this environment variable.
## 2024-05-15 - Fixed Mass Assignment / IDOR Vulnerability in Task Creation
**Vulnerability:** The application was vulnerable to Mass Assignment/Insecure Direct Object Reference (IDOR) during task creation. An attacker could pass a JSON payload with an existing task's `id` field, and Spring Data JPA's `save()` method would interpret it as an update rather than a create, thereby overwriting the existing task's data.
**Learning:** Spring Data JPA's `save()` method acts as an "upsert" (update or insert) depending on the presence and state of the entity's primary key (`id`). If an entity with the given ID already exists, it performs an update. Without explicit protection, incoming payloads containing IDs can overwrite arbitrary existing database records.
**Prevention:** Always explicitly nullify the primary key (e.g., `entity.setId(null)`) on incoming payload entities *before* invoking Spring Data JPA's `save()` method for creation operations. Alternatively, use Data Transfer Objects (DTOs) that do not expose the ID field for creation requests.
