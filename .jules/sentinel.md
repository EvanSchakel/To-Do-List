## 2024-05-08 - Fixed Overly Permissive CORS Configuration
**Vulnerability:** The application was configured with `allowedOrigins("*")` in `WebConfig.java`, which allows any website to make requests to the API.
**Learning:** This architectural gap means the API could be vulnerable to cross-origin attacks because the browser would allow any origin to access the resources. We need to define exactly which origins should have access.
**Prevention:** Avoid hardcoding `*` for CORS origins. Instead, inject the allowed origins using application properties (e.g., `@Value("${cors.allowed-origins}")`), and configure a safe default restrict value (like `http://localhost:3000` for local dev) in `application.properties`. For production environments, override this environment variable.

## 2026-05-19 - Fixed Mass Assignment in Spring Data JPA Task Creation
**Vulnerability:** The application was vulnerable to Mass Assignment (also known as IDOR during creation) in the `TaskService.createTask` method. An attacker could send a POST request to `/api/tasks` with an existing `id` in the JSON payload (e.g., `{"id": 1, "title": "Hacked"}`). Because `taskRepository.save()` in Spring Data JPA defaults to an `upsert` operation when an entity has an ID, this would overwrite the existing task instead of creating a new one.
**Learning:** Spring Data JPA's `save()` method is dual-purpose: it inserts if the entity is new (no ID), and updates if the entity is existing (has an ID). Trusting the incoming ID from a POST (create) payload is a critical security risk.
**Prevention:** Always explicitly nullify the ID field of an incoming entity payload (e.g., `entity.setId(null)`) before calling `.save()` in creation scenarios to force an INSERT operation, or use a separate DTO (Data Transfer Object) that does not include the ID field for creation requests.
